# 升级项目引用的 AtomUI 包

## 何时使用

用户要求升级下游项目引用的 AtomUI NuGet 包时使用。在下游项目中，「请升级 AtomUI 到最新版本」或「把 AtomUI 升到最新版」按依赖升级处理。以用户指定的项目为范围，未指定时使用当前仓库。版本入口、包组和验证命令均从实际项目配置发现。

## 何时不使用

**先判定目标项目所属仓库。** 用仓库维护说明、打包项目的 `PackageId`、发布清单或 CI 确认它是否维护并发布 AtomUI 框架主包，例如 `AtomUI.Core`。目标属于 AtomUI 框架源码仓库时，在选版、还原或修改前结束本 Skill 的流程。该仓库内的测试、样例或 Gallery 即使引用了已发布的框架包，也仍属上游仓库。用户明确指定同一工作区中的独立下游仓库时，以该仓库为判断对象。

仅查询版本、评估升级影响或预演时保持只读。用户明确要求发布上游项目自身的新版本时，使用该项目的发版流程。

## 1. 确定当前生效的依赖

1. 依据用户范围和仓库说明定位消费项目、目标框架与有效构建配置。检查工作区是否已有依赖升级，沿用相关改动并保留无关改动。
2. 从项目实际采用的依赖声明定位版本控制点。使用 MSBuild `PackageReference` 时，检查内联版本、集中版本项、`VersionOverride`、属性导入、条件项和本地覆盖。追踪共享属性是否同时决定消费项目自身的发布版本或范围外引用。用对应配置的锁文件或还原结果确认解析版本，并区分直接与传递依赖。现有还原结果与生效配置对应不上时，重新核实起点。
3. 从项目的有效 NuGet 配置、源映射和还原参数确认每个包的可用来源。共享版本属性或由上游共同发布的包按组处理，独立发布的包分别选版。用实际引用及包的发布信息确认归属。

## 2. 选版并定位发版成果

1. 用户指定的版本或渠道优先。默认选择项目允许的包源中，所需包齐全且适用的最新已列出稳定版。用 NuGet 版本语义比较候选，检查目标框架、依赖区间和生成器资产。保留有效的本地覆盖和包源设置，切换渠道按用户任务范围处理。
2. 按包 ID、版本与来源定位发布记录，通过包内 `.nuspec` 的仓库和提交或已核实的发布标签定位该次发版的文档。NuGet 提供可取得性证据，上游 `project-version-release` 与 `project-release-notes` 形成的正式发布文档提供变更和迁移证据。
3. 当最新候选缺包或与当前项目约束有冲突时，记录缺失的包 ID、版本、来源或具体约束。用户指定的目标无法满足时列为阻塞，默认选版时可采用下一完整且适用的稳定版。继续处理可独立升级的组。

## 3. 逐版读取 API Break 文档

1. 对每个发布单元，从当前生效版本之后到目标版本为止，按发布线和版本顺序列出跨过的正式发布条目。预发布或本地渠道按已选渠道核对其发布记录，`Unreleased` 条目排除在正式版升级范围之外。
2. **逐版读取实际发布的 API Break 文档。** 从 Changelog 的 `Breaking Changes` 和发布索引进入对应文件，沿用上游实际路径。常见入口为 `CHANGELOG.zh-CN.md` 或 `CHANGELOG.md`、`docs/releases/overview.md`，以及 `docs/releases/<release-key>-api-changes.zh-CN.md` 或对应英文版。目标版指南通常只覆盖其声明的基线，因此每个中间版都要核对。
3. 对每条适用变化记录文档版本与章节、旧用法、新用法、下游命中位置和验证动作。检查 C#、XAML、生成注册、目标框架、打包和运行行为。将仍适用于目标版的迁移动作合并到一次升级。
4. 文档缺失或与实际发布包冲突时，使用同版本的发版记录、可用的 `docs/engineering/evidence/releases/<release-key>-api-break-audit.md`、包内容或对应源码差异补证。记录已核实的事实和待核实的条目。仍缺证据的变化只阻塞受影响的项目或包组。

## 4. 应用并验证升级

1. 更新实际控制版本的位置和已命中的迁移点。保留精确版本、区间和 Analyzer 资产的约束语义。共享属性的联动超出用户范围时，按项目允许的方式独立调整引用版本，并复核原有版本的生效值。项目要求版本同步时，说明联动及其对本次升级的影响。按项目规则调整上游要求的配套依赖。传递依赖通过实际引入它的上游引用调整。项目使用锁文件时，用既有 NuGet 还原流程更新受影响的锁文件，并按项目配置复核锁定还原。
2. 从项目维护说明、构建配置和 CI 找到现有升级与验证入口，核对入口的生效配置、覆盖范围和副作用。复用适用的项目命令。缺少专用入口时，用项目选定的 SDK 对受影响入口执行还原、构建和相关测试。
3. 核对受影响目标框架和配置的实际解析版本，并用还原记录或包来源证据确认实际包源。按迁移要求验证生成注册、API 或运行行为。涉及包资产、下游包消费、裁剪或 NativeAOT 时，执行项目适用的对应验证。复用与当前输入和配置一致的验证证据。版本与渠道已对齐、迁移已落实时跳过写入。
4. 交付每个项目的旧版与新版、实际包源、API Break 文档覆盖范围、已做的迁移、实际验证命令及结果。用未解决的具体条目标明失败、未运行或仍受阻的范围。

## 示例

用户说「请升级 AtomUI 到最新版本」。当前消费项目使用 `6.2.13`，包源中适用于该项目且包组齐全的最新稳定版为 `6.2.15`。从项目的导入属性找到版本控制点，按发布索引读取 `6.2.14` 和 `6.2.15` 的 API Break 文档。应用前者要求的 Avalonia `12.1.6`，同步升级后者涉及的 AtomUI 包及生成器。若消费项目使用生成注册，重新编译并通过其已有测试验证注册入口。报告引用两版迁移章节、实际解析版本和测试结果。
